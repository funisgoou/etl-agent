## 1. 概述

### 1.1 设计目标

1. 支撑控制面全部治理流程：用户/项目/权限、连接与元数据探查、Pipeline 生成与不可变版本化、`prepare → approve → commit` 三阶段协议、Celery 异步执行与运行监督。
2. 满足 Harness 安全内核的对抗性要求（D2）：Capability 单次消费 nonce 存证、证据账本哈希链可校验、不可变制品摘要、Transactional Outbox 原子投递。
3. 支撑哑管道 + 受管 SQL 分流的数据面模型（D5）：Doris 侧 `{t}__raw` / `{t}__shadow` / `{t}__err` / 正式表与 `tmp_dry_run` 库。
4. 保证三层状态隔离：对话状态、LangGraph Workflow State（PostgresSaver checkpoint，恢复唯一真相源，D10）、Execution State（`execution_runs` 等）。

### 1.2 存储体系总览（多模持久化）

| 存储 | 角色 | 承载内容 |
| --- | --- | --- |
| PostgreSQL | 控制面元数据库 | 全部业务表（第 3 章）、LangGraph checkpoint 表（第 4 章）、Outbox / Capability / 证据账本 |
| Doris | 数据面数仓 | `{t}__raw` / `{t}__shadow` / `{t}__err` / 正式表 / `tmp_dry_run` 库（第 6 章） |
| MySQL | **业务源库（本地开发演示）** | 演示业务库 `biz_demo` 及种子数据（第 7 章），作为 MySQL→Doris 链路源端 |
| MinIO | 对象存储 | CSV 文件资产（S3A 协议供 SeaTunnel 消费，C3） |
| Redis | 缓存 / 消息 | Celery Broker、运行状态 pub/sub（SSE 回传通道，D7） |

**边界原则**：控制面不直连搬运业务数据；业务数据只存在于源端（本地开发阶段为 MySQL `biz_demo` 与 MinIO CSV）、Doris 与 MinIO。PostgreSQL 中只保存元数据、指纹、摘要、指标与审计证据。

### 1.3 命名与通用约定

- 表名：小写蛇形复数；主键统一为 `id BIGINT GENERATED BY DEFAULT AS IDENTITY`。
- 时间字段：`TIMESTAMPTZ`，默认 `now()`；`created_at` 不变，`updated_at` 由应用层或触发器维护。
- JSON 字段：一律 `JSONB`（`*_json`），结构化契约（EtlPlan、QualityContract、预算等）以 JSONB 入库。
- 摘要/哈希字段：`CHAR(64)` 存十六进制 SHA256（`artifact_digest`、`payload_digest`、`token_digest`、`event_hash` 等）。
- 枚举：用 `TEXT` + `CHECK` 约束表达，不建 PostgreSQL ENUM 类型，便于后续扩展。
- 金额/字节/行数：`BIGINT`，禁止 `FLOAT` 存计量值。
- 所有外键 `ON DELETE RESTRICT`（默认）：治理数据禁止级联删除；作废走状态字段。
- `audit_events` 为只追加表：禁止 UPDATE/DELETE（数据库层面用权限 + 触发器强制）。

## 2. 实体关系总览

```
users ──┬── project_memberships ── projects
        ├── project_role_grants ── projects
        └── sessions

projects ──┬── connections ── metadata_profiles
           ├── file_assets
           └── pipelines ── pipeline_versions ──┬── pipeline_artifacts
                                                ├── agent_runs
                                                └── preparations ──┬── approval_requests
                                                                   └── execution_runs ── runtime_supervision_snapshots

capability_tokens（独立，经 token_digest 被 execution_runs 引用）
outbox_events（独立，aggregate_id 逻辑指向 execution_runs 等聚合）
audit_events（project_id 逻辑关联，哈希链自引用 prev_event_hash）
benchmark_cases（独立）  benchmark_runs（独立）
evolution_candidates（project_id 逻辑关联）  gray_flags（project_id 逻辑关联）
```

> `capability_tokens`、`outbox_events`、`audit_events`、`benchmark_*` 不建物理外键（安全内核要求解耦与只追加），关联靠应用层逻辑键。

### 3.4 审批与执行

#### preparations

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK | |
| version_id | BIGINT | NOT NULL, FK→pipeline_versions | |
| maker_id | BIGINT | NOT NULL, FK→users | 准备单申请人（Maker）；Approve 时据此判定禁止自批 |
| expires_at | TIMESTAMPTZ | NOT NULL | 准备单过期时间（TTL 默认 72 小时，配置项 `preparation_ttl_hours`） |
| input_fingerprint | CHAR(64) | NOT NULL | 输入指纹 SHA256，Commit 时重算比对 |
| resource_scope | JSONB | NOT NULL | 资源范围（连接、库表、文件等） |
| impact_json | JSONB | NOT NULL | 影响范围分析 |
| data_classification | VARCHAR(16) | NOT NULL | 数据分级：`public` / `internal` / `confidential` / `secret` |
| budget_json | JSONB | NOT NULL | 冻结预算：最大读取行数、最大写入字节数、最大执行时长 |
| rollback_plan_json | JSONB | NOT NULL | 回滚方案 |
| risk_level | VARCHAR(4) | NOT NULL | PDP 输出：`P0` / `P1` / `P2` / `P3` |
| status | VARCHAR(24) | NOT NULL DEFAULT 'pending' | `pending` / `approved` / `rejected` / `committed` / `expired` / `cancelled` |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

- 索引：`INDEX (version_id, status)`。
- 冻结语义：Prepare 完成后除 `status` 外字段禁止变更；指纹在 Commit 时重新比对，不一致则拒绝。
- TTL 机制：`expires_at` 默认签发后 72 小时（配置项 `preparation_ttl_hours`）；Celery Beat 周期任务将过期的 `pending` / `approved` 单置 `expired` 并写证据账本；Commit 时检查未过期，否则报 `E_PREP_EXPIRED`。

| preparation_id | BIGINT | NOT NULL, FK→preparations | |

| decided_at | TIMESTAMPTZ | | |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

- 唯一约束：`UNIQUE (preparation_id, required_role)`（同一准备单同一职责槽一张审批单）。
- 职责槽互斥（D3）在服务端判定：同一 Preparation 内 `approver_id` 不得与 Maker 及另一职责槽审批人重复；申请人禁止自批。

#### capability_tokens

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK | |
| token_digest | CHAR(64) | NOT NULL, UNIQUE | 令牌本体 SHA256；**明文令牌不落库** |
| subject_id | BIGINT | NOT NULL | 主体（操作员 user_id / 系统主体） |
| tool_intent | VARCHAR(64) | NOT NULL | 绑定工具意图：`execute_pipeline` / `dry_run` / `rollback` / `cleanup` 等 |
| artifact_digest | CHAR(64) | NOT NULL | 绑定制品指纹 |
| nonce | VARCHAR(64) | NOT NULL, UNIQUE | **nonce 存证**（D2，生产级防重放，禁止 Redis SETNX 替代） |
| expires_at | TIMESTAMPTZ | NOT NULL | 有效期 5 分钟 |
| consumed_at | TIMESTAMPTZ | | 消费时间；Replay Guard 在消费事务中将其原子置位 |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | 只追加 |

- 单次消费由数据库保证：`UPDATE ... SET consumed_at = now() WHERE id = ? AND consumed_at IS NULL AND expires_at > now()`，影响行数为 0 即拒绝（重放/过期）。
- 签名（Ed25519）在令牌本体（JWT 式结构）内，服务端验签 + 本表存证双重校验。

#### execution_runs

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK | |
| version_id | BIGINT | NOT NULL, FK→pipeline_versions | |
| preparation_id | BIGINT | FK→preparations | 可空（`run_kind='dry_run'` 时为空） |
| run_kind | VARCHAR(16) | NOT NULL DEFAULT 'execute' | 运行类型：`execute` / `dry_run`；Dry-Run 不创建准备单（免四眼），但仍签发 Capability、进证据账本 |
| capability_token_digest | CHAR(64) | NOT NULL | 逻辑关联 capability_tokens.token_digest |
| status | VARCHAR(24) | NOT NULL | 主状态：`pending` / `running` / `succeeded` / `failed` / `cancelled` / `rolled_back` |
| sub_stage | VARCHAR(16) | | 子阶段，仅 `running` 时取值 `COPYING` / `SPLITTING` / `SWAPPING`，Worker 分阶段持久化 |
| engine_job_id | VARCHAR(128) | | SeaTunnel 作业 ID |
| input_records | BIGINT | | 读取行数 |
| output_records | BIGINT | | 写入行数（合格行） |
| error_records | BIGINT | | 分流至 `__err` 行数 |
| bytes_processed | BIGINT | | 处理字节数 |
| diagnosis_json | JSONB | | 失败/监督中断时由诊断服务写回，含 root_cause、suggestions；`GET /execution-runs/{id}` 响应以 `diagnosis` 字段透出 |
| started_at / finished_at | TIMESTAMPTZ | | |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

- 索引：`INDEX (version_id, status)`、`INDEX (preparation_id)`。
- CHECK 约束（`run_kind` 与 `preparation_id` 联动）：`run_kind='execute'` → `preparation_id NOT NULL`；`run_kind='dry_run'` → `preparation_id IS NULL`。
- 行数硬判据（C1）双等式校验：① `input_records == 源端行数`（Dry-Run 时为 `min(源端行数, 采样上限 dry_run_sample_limit)`）；② `output_records + error_records == input_records`（合格行进 `__shadow`、违规行进 `__err`，合计须等于读取行数）。任一不满足即判失败。
- Commit 时与对应 `outbox_events` 在同一 PostgreSQL 事务中原子写入。

### 3.5 审计与评测

#### audit_events

## 4. LangGraph Checkpoint 表（PostgresSaver）

- 由 LangGraph `PostgresSaver` 自动建表与维护（`checkpoints` 及其附属表），**应用代码不手写 DDL、不直接读写**。

## 5. 关键数据机制设计

### 5.1 证据账本哈希链（audit_events）

- 事件写入：`event_hash = SHA256(prev_event_hash ‖ canonical(event))`，同一 project 内串行追加（可用 `SELECT ... FOR UPDATE` 锁项目尾事件或单写者约束）。
- 创世事件：`prev_event_hash` 取固定常量（64 个 `0`）。
- 校验：`GET /api/v1/audit/verify` 按 `id` 升序重算全链，报告第一个断点位置与期望/实际哈希（篡改演示验收入口，D9）。

### 5.2 Capability 单次消费与防重放

- 令牌本体：Ed25519 签名，声明 `tool_intent`、`subject_id`、`artifact_digest`、`nonce`、`expires_at`（5 分钟）。
- 存证：`capability_tokens` 落 `token_digest` + `nonce`（双 UNIQUE），明文令牌与私钥不落库。
- 消费：Tool Broker 验签后，在单事务中原子 `consumed_at` 置位（5.3 节 SQL 形态），重放/过期/跨意图/跨指纹一律拒绝并写审计事件。

### 5.3 不变性与只追加约束（触发器）

对以下表/行强制只追加或冻结（触发器 `BEFORE UPDATE OR DELETE` 抛错）：

- `audit_events`、`capability_tokens`、`outbox_events`（仅允许 `status`/`published_at` 的受限迁移，用列白名单判定）、`runtime_supervision_snapshots`、`metadata_profiles`。
- `pipeline_versions`：当 `OLD.is_immutable = true` 时禁止 UPDATE/DELETE。
- `preparations`：仅允许 `status` 字段迁移，其余字段冻结。

### 5.4 Transactional Outbox

- Commit 在一个 PostgreSQL 事务内完成：`preparations.status → committed` + 插 `execution_runs` + 插 `outbox_events(status=pending)`。
- Worker/中继进程捞取 pending 事件投递 Celery，成功后置 `published`；失败重试，保证投递不丢。

### 5.5 QualityContract 与编译产物

- `pipeline_versions.etl_plan_json` 内含 QualityContract 契约 JSON（字段、算子、阈值、错误码）；**禁止手写 SQL 字符串入库**。
- 分流 SQL 由编译器按 Doris 方言**确定性生成**，作为 `pipeline_artifacts`（`artifact_type = 'quality_contract_sql'`）落库，形态固定：`INSERT INTO {t}__shadow|__err SELECT ... FROM {t}__raw`；门禁校验编译器输出。

### 5.6 凭据与脱敏

- `connections.config_json` 中密码/密钥仅存 Vault KV v2 引用路径，Worker 执行时经 SecretProvider 物化，全链路无明文落库；API 响应一律掩码。
- `metadata_profiles.masked_sample_json` 只存脱敏样本。

## 6. 数据面存储设计

### 6.1 Doris 表族（每个受管目标表 {t}）

| 表 | 角色 | 生命周期 |
| --- | --- | --- |
| `{t}__raw` | SeaTunnel 单 sink 全量落点（哑管道，无行级判断） | 每次 run 按 run 隔离（truncate 或 run_id 分区），安全重跑不重复计数 |
| `{t}__shadow` | 受管 SQL 分流后的合格行 | 原子 Swap 的唯一来源 |
| `{t}__err` | 违规行 + 错误码 + 原始值 + 违规原因（留存证据） | **不参与 Swap**，按项目保留策略清理 |
| `{t}`（正式表） | 对外服务表 | 仅经 `REPLACE TABLE ... swap=true`（或等价原子交换）由 `__shadow` 发布 |
| `tmp_dry_run` 库 | Dry-Run 临时表（COPY + SPLIT，跳过 Swap） | 跑完可清理 |

- `{t}__err` 在源 Schema 之上追加受管列：`__run_id`、`__error_code`、`__error_reason`、`__raw_payload`（原始值 JSON）、`__created_at`。
- 脱敏（如邮箱）在分流 SQL 的 SELECT 列表内完成，不进入 SeaTunnel transform。

### 6.2 MinIO 对象布局

- Bucket：`etl-assets`；对象键：`projects/{project_id}/file_assets/{file_asset_id}/{file_name}`。
- `file_assets.file_path` 记录 S3A 完整路径（`s3a://etl-assets/...`），SeaTunnel 经 S3 连接器消费（C3）；统一存 MinIO，不做双写。

### 6.3 Redis 键设计

| 键 / 通道 | 类型 | 用途 |
| --- | --- | --- |
| Celery Broker | 队列 | 异步任务（执行、Dry-Run、回滚、清理） |
| `exec_run:{run_id}` | pub/sub channel | Worker 回传运行状态，FastAPI SSE 接口转发（D7） |

- Redis **不承担**防重放/nonce 存证职责（D2 禁止 SETNX 式简化）。

## 7. 业务演示库设计（MySQL，本地开发环境）

### 7.1 定位与约束

- 本地开发环境无真实业务数据，MySQL 中的 `biz_demo` 库作为 **MySQL→Doris 端到端演示链路的源端业务库**；CSV→Doris 链路源端为演示 CSV 文件（经 MinIO，见 7.4）。

### 7.2 库级约定

- 库名：`biz_demo`；字符集 `utf8mb4` / `utf8mb4_0900_ai_ci`；引擎 InnoDB。
- 主键统一 `id BIGINT AUTO_INCREMENT`；时间字段 `DATETIME DEFAULT CURRENT_TIMESTAMP`。

### 7.5 种子数据（造数）规则

- 规模：customers ≈ 200 行、orders ≈ 1000 行、products.csv ≈ 100 行；造数脚本参数化，可放大用于性能演示（Dry-Run 默认采样 LIMIT 1000）。

| products.csv | `price < 0` / 空 `sku` | ≈4% | `E_NOT_POSITIVE` / `E_NOT_NULL` |

- 每张表的**合法行数 / 违规行数预期值作为基准常量**随造数脚本产出，供运行中心质量报告与 Benchmark 断言比对。
