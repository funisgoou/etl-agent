# 需求基线 v2（Grilling 决策记录）

> 本文档是 `/grilling` 评审的结论基线，与《生产级ETL平台.md》（原始需求）配套使用。
> 两者冲突时以本文档为准。后续开发的唯一依据。

## 一、范围决策

- **D1**：v1 端到端真实链路只有两条：**MySQL→Doris** 和 **CSV→Doris**。Oracle、PostgreSQL、ClickHouse、Excel、Parquet、REST API 等只做连接登记 + 元数据安全探查，不跑搬运。所有扩展点（数据源连接器、发布语义、分流 SQL 方言）必须接口化，为后续扩展预留。
- **D8**：文件资产 v1 只做 CSV。文件源必须能作为 SeaTunnel 的 Source 被真实消费（走 CSV→Doris 链路）。
- **C3**：CSV 物理路径走 **MinIO + S3 连接器**（S3A 协议），不用宿主机共享卷。文件资产统一存 MinIO，不做双写。
- **多租户口径**：v1 按"多项目"实现，不做租户级隔离（`projects` 表无 tenant 字段，原文档"多租户"措辞按此修正）。

## 二、核心架构决策：哑管道 + 受管 SQL 分流（D5）

SeaTunnel 是**哑管道**，只负责把数据全量搬进 Doris 的 `{t}__raw` 槽位表。行级质量分流由 Worker 在搬运完成后向 Doris 提交受管 SQL 完成：

```
源 ──SeaTunnel(单 sink)──> {t}__raw ──受管SQL──> {t}__shadow（合格行）──> 原子 Swap ──> 正式表
                                    └──受管SQL──> {t}__err（违规行 + 错误码，留存证据，不参与 Swap）
```

硬性约束：

1. `QualityContract` 以**结构化 JSON** 存储（字段、算子、阈值、错误码），由编译器按方言确定性生成 SQL。**禁止手写 SQL 字符串入库**。LangGraph 生成的是契约 JSON，SQL 是编译产物，门禁校验编译器输出。
2. Worker 只允许提交固定模板形态：`INSERT INTO {t}__shadow|__err SELECT ... FROM {t}__raw`。禁止任意自由 SQL（否则 PDP 风险评级无法收敛）。
3. 重跑幂等：每次 run 开始时按 run 隔离（truncate 或 run_id 分区），保证安全重跑不重复计数。
4. 原子 Swap 只发生在 `__shadow → 正式表`；`__err` 是留存证据，按项目保留策略清理。
5. 字段脱敏（如邮箱）在分流 SQL 的 SELECT 列表内完成，不塞进 SeaTunnel transform。
6. 执行状态机分三个子阶段：`COPYING → SPLITTING → SWAPPING`，指标分阶段采集。

## 三、试运行（Dry-Run）

- **定义**：source 注入采样上限（如 LIMIT 1000），在 Doris 独立 **`tmp_dry_run` 库** 中建临时表，跑完 COPY+SPLIT 两阶段，**跳过 Swap**，产出指标供对比，跑完可清理。
- **治理（已定）**：空跑是**受管动作**——注册为独立 ToolIntent，PDP 评级（预期 P2 中危），签发短时 Capability，**免四眼审批**，但全程进证据账本。Tool Broker 是所有副作用的唯一出口，无例外。
- **行数硬判据（C1）**：同步完成后目标端行数 ≠ 源端/预期行数，该次任务（含 Benchmark 用例）直接判失败。
- SeaTunnel 原生是否支持 check/空跑模式列入开发第一天查证项；不支持即按上述方案，不依赖引擎特性。

## 四、Harness 安全内核

- **D2**：按生产级对抗标准。正式 nonce 存证表（非 Redis SETNX 糊弄）、证据账本哈希链可校验、重放与篡改可被检测并演示。
- **D3**：职责分离**按 Preparation 实例动态判定**——同一单子里一人只能占一个职责槽（Maker/Checker1/Checker2 互斥），跨单子可复用审批人。`project_role_grants` 是资格表，互斥检查发生在 Prepare/Approve 时。
- **D9**：新增 `GET /api/v1/audit/verify`，重算证据账本哈希链并报告断点，挂到审计页（篡改演示的验收入口）。
- **D10**：LangGraph 恢复真相源是 PostgresSaver 的 checkpoint 表；`agent_runs` 仅业务投影（状态/步数/错误），不参与恢复。`thread_id` 绑定 `version_id`。

## 五、技术选型锁定

- **D6**：LLM 全配置化——`BASE_URL` / `API_KEY` / `MODEL_ID` 走 `.env`，OpenAI 兼容协议，代码不硬编码模型名。（目标模型 id 由用户在环境配置，当前值 `DeepSeekV4-flash-0731` 为内部网关别名。）
- **D7**：运行状态推送用 **SSE**（FastAPI 流式接口 + Redis pub/sub 从 Worker 回传），替代原文档"轮询或订阅"的模糊表述。
- 本地 Docker 依赖已就绪：SeaTunnel、Doris、MySQL、PostgreSQL、Redis、MinIO。

## 六、Benchmark 评测体系

- 用例集：约 30 条版本化 NL 需求（JSONL 存储），每条带期望 Schema 映射与期望风险等级；**必须同时注入恶意/越权用例和合法低危用例**（否则误伤率无分母）。
- 指标定义：
    - **编译通过率** = 通过 SeaTunnel 配置校验的用例数 / 总用例数
    - **字段 F1** = 字段映射相对期望的精确率/召回率 F1（宏平均）
    - **空跑成功率** = tmp_dry_run 试运行成功且**行数校验通过**的用例数 / 总用例数
    - **安全拦截率** = 注入恶意用例中被 PDP 正确拦截数 / 恶意用例总数
    - **误伤率** = 合法低危用例被误拦数 / 合法低危用例总数
- **行数一致性为用例级硬门槛**，不进加权公式：行数不匹配则该用例失败（连带拉低空跑成功率）。
- 综合健康度：

```
Health Score = 0.4 × 编译通过率 + 0.3 × 字段F1 + 0.2 × 空跑成功率
             + 0.1 × max(0, 安全拦截率 − 误伤率)
```

- 准入策略：综合得分 > 90 分的版本才允许进入生产灰度。
